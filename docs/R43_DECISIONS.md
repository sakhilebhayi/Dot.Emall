# R-43 decisions taken without the owner

The owner asked for an uninterrupted build. Each decision below is the safest, most reversible choice, with how to reverse it. Add new ones at the end with the reasoning.

| # | Question (source) | Decision | Reverse by |
|---|---|---|---|
| D-1 | Refuse checkout in production while Paystack is not configured? (audit R-02) | **Yes.** `config('emall.checkout.requires_gateway')` defaults to true in production; without a usable key checkout answers "Payments are not open yet" and no unpaid order can be shipped. | env `EMALL_CHECKOUT_REQUIRES_GATEWAY=false` |
| D-2 | Seller money, commission, payouts (R-01) | **Internal ledger, no automated payouts.** Each seller group in a paid order writes a ledger entry (gross, platform commission, net, status held/released). Commission is `config('emall.commission.percent')`, **default 0** (no business term is invented); the seller sees the full fee before publishing and on every order; entries release 7 days after delivery. Paystack transfers/subaccounts and KYC are an owner item. | set the percent; build payouts later |
| D-3 | VAT and shipping (R-03) | Displayed prices are **VAT inclusive**. Stores have `vat_registered` and a claimed `vat_number` (default off); when registered, order documents show the VAT component at `config('emall.vat.rate')` (0.15). Shipping is **per-store methods** (flat, free over a threshold, collection) with optional region rules; the cart shows delivery per seller group and a total before payment. | config / seller settings |
| D-4 | Stock hold and unpaid-order cap (R-05, R-06) | Stock is held **30 minutes** (`EMALL_STOCK_HOLD_MINUTES`), extended while a payment attempt is open; at most **3 unpaid orders** per buyer or guest e-mail at once (`EMALL_MAX_UNPAID_ORDERS`). | env |
| D-5 | What "Delivered" means (R-08) | A seller must mark **Shipped** (with optional carrier and tracking number) before **Delivered**; collection orders go Ready for collection then Collected. The **buyer may confirm receipt**. Reviews unlock and the return window starts at Delivered; ledger release is 7 days after Delivered. No direct Pending to Delivered jump. | state machine |
| D-6 | Returns (R-10) | Return request **within 7 days of delivery** per order item (adopted from ECTA s44 as a standard, not a legal claim); reasons: faulty/not as described (seller pays return) or changed mind (buyer pays); seller approves or declines **with a stated reason**; unanswered for 10 days it escalates to the operator queue; an approved return, once the seller marks it received, refunds through the existing refund service. | config |
| D-7 | Account deletion (R-12) | Refused while orders, returns or refunds are open; otherwise anonymise the person and keep order and financial records. | policy |
| D-8 | Second hostname (R-?) | `TRUSTED_HOSTS` defaults to the `APP_URL` host (emall.infodot.co.za). If `emall.infodot.app` is also served, add it to the host `.env` before deploying. | env |
| D-9 | Guests | Guests browse, keep a session cart and check out with an e-mail; they follow the order by a signed magic link; orders attach to an account when someone signs in through InfoDot with the same verified e-mail. | middleware |
| D-10 | Reference prices | "Was" price = lowest recorded price in the previous 30 days from `product_price_history`, shown only when it is higher than today's price and the history is at least 30 days old; never a seller-typed original price. | feature flag |
| D-11 | Recommendations | Only from real orders and views, with minimum counts (default 3 co-purchases), labelled with the real basis and number. | config |
| D-12 | Registration | Stays closed; accounts come from InfoDot. CTAs say so. | feature |
| D-13 | Dependencies | Patch-level `composer update` of the Symfony packages flagged by `composer audit`, and `npm audit fix` without `--force`. | revert lock |
| D-30 | Which PostgreSQL features does search need? (data agent B) | **Only what every PostgreSQL has.** Full-text search (`tsvector`, GIN) is built in and needs no extension. Text is lowercased, accent-stripped and plural-folded in PHP before it is stored and searched, so the `unaccent` extension is not used. `pg_trgm` is optional: the migration tries to create it inside a savepoint, and without it typo correction uses an edit-distance scan of the catalogue's own vocabulary (same answers, slower on very large vocabularies). SQLite and any host where the tsvector column is missing use `PortableSearch`. `DISCOVERY_SEARCH_ENGINE=portable` forces it. | env |
| D-31 | What counts as a real purchase for any figure shown to a shopper? | One definition in `CountedOrders`: a non-cancelled line whose order is paid or partially refunded, or whose order never required payment (placed before the gateway was configured) and whose line is delivered. Pending, unpaid, failed and fully refunded orders never count. Used by best-selling, bought-together, trending, reorder, GMV and the other metrics. | edit one class |
| D-32 | Behaviour tracking and privacy | Recently viewed, search history and funnel events store a **keyed hash** (HMAC of the user id, or of a random session token) and never a user id or e-mail. Search text that looks like an e-mail address or a long number is not stored. Search history and product views are deleted after 90 days, events after 400 (`emall:discovery-prune`, scheduled daily). "Popular searches" need 3 different people and a result; "recent searches" are the person's own. A visitor's activity moves to their account at sign-in. | config |
| D-33 | Facet counts cost a scan; cache them? | Facet counts are cached for 60 seconds **in production only** (`DISCOVERY_FACET_CACHE_SECONDS`), off elsewhere so tests and demos see their own writes. | env |
| D-34 | Recommendation thresholds | Bought together: 3 distinct counted orders. Viewed together: 5 distinct people. Window 180 days. Orders with more than 30 lines are ignored as bulk. Links are precomputed hourly into `product_relations` (replaced in one transaction). Below a minimum, nothing is shown. Editorial "often needed with" rules are labelled as ours and carry no number. | config |
| D-35 | Alerts and consent | Subscribing to an alert is the consent: one person, one product, one thing. Back in stock fires once and is spent. Price drop fires once per new low against the price the person saw when they subscribed (stored on the alert), and quotes the lowest recorded 30-day price only when the commerce price-history table exists. Saved-search digests are off by default and are daily or weekly at most, with new matches only. All checks go through `NotificationPreferences` (default: allow). | bind a preference store |
| D-36 | Review integrity | The verified flag and the order line are written by `ReviewService` from a delivered line; the request cannot set them. A review is **held** (not rejected) for the operator when the person posts more than 3 in 24 hours, or posts copied text (same person, 90% similar; or another account's word-for-word text of 40+ characters). Held and removed reviews do not move ratings or appear. Authors can edit for 30 days. A store rating shows from 5 published reviews. Review photos (4 max, 4 MB, re-encoded) live on the private disk and are streamed by `ReviewPhotoController`. No IP or account-age signal is used because none is recorded. | config |
| D-37 | Product Q&A rules | Signed-in non-sellers only, 10 to 500 characters, one question per person per product per day. A question with a link, e-mail address or phone number is held for the operator. Only the store's owner and the members of a team the owner leads can answer (`StoreMembers`); nobody but the operator can hide an answer, and sellers cannot delete one. Reports never hide anything by themselves; the operator resolves them. | policy |
| D-38 | Shopping assistant | Deterministic by default. Words such as "reliable" or "cheapest" steer the sort; "for university" is repeated back and explicitly **not** treated as knowledge about suitability. With `ANTHROPIC_API_KEY` set a model may rewrite the explanation and propose narrowing, but each line is accepted only if every number in it is in that product's facts (or the shopper's budget), it names no other product, has no link and none of a list of unsupportable claims (warranty, guarantee, free delivery ...). Rejected lines fall back to the rule text; the answer says `mode: rules` or `model`. Without the key nothing leaves the server. | env |
| D-39 | Dot.Analytics extra keys | Engagement counts (`product_views_7d`, `add_to_cart_7d`, `wishlist_adds_7d`) are added to the daily snapshot only when `ANALYTICS_COMMERCE_METRICS=true`, because Dot.Analytics must be told to accept them. Off by default so the existing contract is unchanged. | env |
| D-40 | Seams to the commerce data workstream | Brands, attributes, store regions, price history and delivery estimates are read through `App\Contracts\CatalogueSource`; categories through `CategoryTree`; preferences through `NotificationPreferences`. The defaults check the schema before reading and answer "nothing known" for what does not exist, so the two branches merge cleanly and reconciliation is one class (`DatabaseCatalogueSource`). | bind another implementation |
| D-41 | JSON endpoints and validation | The app renders JSON errors only under `/api`, so the suggest and assistant controllers validate by hand and answer 422 JSON themselves. | n/a |
